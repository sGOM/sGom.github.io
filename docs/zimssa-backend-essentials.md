# 짐싸(ZIMSSA) 백엔드 개발자가 알아야 할 것

이사 중개 플랫폼 짐싸의 백엔드 포지션을 기준으로, 회사·도메인·기술을 정리한 문서다.

**출처 기준.** 회사와 채용 공고에 관한 내용은 공개된 자료에서 확인한 사실만 적고 문서 끝에 출처를 단다.
짐싸 내부의 아키텍처·인프라·코드 구조는 **공개된 자료가 없다.** 3장 이후는 공고에 명시된 스택과
이사 중개 도메인의 구조에서 끌어낸 내용이며, 짐싸의 실제 구현이라는 근거는 없다. 이 구분을 문장마다 `사실`/`추정`으로
표기하지 않고, 1~2장을 사실, 3장 이후를 일반론과 추정으로 나눠 배치했다.

### 1.2 서비스 구조

짐싸는 이사를 앞둔 고객과 이사 업체(파트너)를 앱 안에서 매칭하는 **양면 시장(two-sided marketplace)** 이다.
전화나 방문 실사 없이 앱에서 견적 신청·비교·예약까지 끝내는 **All-in-App** 을 내세운다.

흐름은 이렇다.

1. 고객이 출발지·도착지·이사 날짜·짐 정보를 입력한다. 짐을 품목으로 고르거나 방 사진을 찍어 올린다.
2. 요청이 파트너에게 열린다. 고객은 **최대 5명**의 파트너 견적을 받는다.
3. 고객이 파트너 프로필·후기·평점·가격을 비교해 직접 고른다.
4. 앱에서 거래를 확정하면 **안심예약**이 자동 적용된다. 별도 신청이나 조건이 없다.
5. 이사 현장에서 문제가 생기면 짐싸가 중재·조정하고, 안심플러스 보상 제도로 처리한다.
6. 이사 후 후기와 평점이 쌓이고, 그게 다음 고객의 비교 기준이 된다.

취급 상품은 원룸이사, 소형이사, 가정이사, 포장이사, 반포장이사, 용달이사이고,
여기에 입주청소와 인터넷 상품 비교·가입이 붙는다.

### 1.3 규모와 성장

| 시점 | 지표 |
|---|---|
| 2019년 초 | 누적 이사 신청 20만 건 |
| 2020년 초 | 누적 이사 신청 50만 건 |
| 2021년 초 | 누적 이사 신청 100만 건 |
| 2021년 | 앱 누적 다운로드 100만, 이후 1년여 만에 150만 |
| 2024년 4월 | 활동 파트너 1,300개 이상 |
| 최근 | 누적 서비스 요청 300만 건, 누적 거래액 2,600억 원 |

수도권에서 시작해 부산·대구·대전을 열고 전국으로 넓히는 방향이다.
주력이던 소형이사에서 가정이사와 이사청소로 카테고리를 확장했다.

### 1.4 백엔드 관점에서 읽어야 할 지점

위 숫자는 마케팅 문구가 아니라 시스템 요구사항이다.

- **누적 300만 건, 파트너 1,300+.** 초당 요청 수로 보면 크지 않다. 대형 트래픽 문제가 아니라
  **정합성과 상태 관리**가 어려운 규모다. 건당 금액이 수십~수백만 원이고 물리 작업이 뒤따르므로,
  한 건이 잘못되면 사용자에게 실제 손해가 발생한다.
- **거래액 2,600억.** 정산과 정합성이 핵심이다. 통계가 틀리는 것과 정산이 틀리는 것은 무게가 다르다.
- **최대 5개 견적 / 파트너가 입찰.** 동시성 문제가 정확히 여기 있다. 5개 마감, 중복 배정, 선착순 경합.
- **중재·보상 제도.** 분쟁이 제도로 존재한다는 건, 시스템이 **누가 언제 무엇을 했는지 증명**할 수 있어야
  한다는 뜻이다. 이력 테이블과 감사 로그가 부가 기능이 아니라 요건이다.
- **카테고리·지역 확장.** 이사만 있던 모델에 청소·인터넷이 붙는다. 도메인 모델이 상품 유형에
  얼마나 열려 있는지가 계속 시험대에 오른다.

## 2. 채용 공고가 요구하는 것

공고(백엔드 개발자, 신입~6년)에서 확인되는 내용이다.

### 2.1 주요 업무

- 짐싸의 비전을 이해하고 서비스의 **신뢰성·안정성·확장성**을 책임지는 백엔드 시스템 개발
- **인프라, DB 관리, API 개발** 등 핵심 역할 수행
- **높은 가용성과 확장성**을 갖도록 백엔드 시스템 개발 및 개선
- **요구사항 분석 및 테스트**를 통한 RESTful API 구축
- 서비스 성능을 위한 **애플리케이션 최적화**

### 2.2 자격 요건

- **Spring Boot(Java), JPA 기반 서비스의 개발·운영 경험 2년 이상 6년 이하**
- **DB(RDB, NoSQL) 테이블 설계** 가능
- 새로운 기술을 두려워하지 않을 것
- 자신의 생각을 논리적으로 제시하고 설득할 수 있을 것
- Slack, Notion, Jira 기반으로 능동적으로 커뮤니케이션·협업할 수 있을 것
- 팀 단위로 일을 진행하고 결과를 만들어낼 수 있을 것

### 2.3 우대 사항

- 기존 시스템의 문제점을 발견해 개선하고, 새로운 과제를 끈기 있게 추적해 해결하는 것을 즐기는 사람

### 2.4 공고 문장을 기술 항목으로 번역하면

| 공고 문장 | 실제로 물어보는 것 |

## 3. 도메인 모델 — 이사 중개 플랫폼의 백엔드

여기서부터는 짐싸 내부 구현이 아니라, 이 도메인을 백엔드로 옮길 때 반드시 마주치는 구조다.

### 3.1 핵심 애그리게이트

| 애그리게이트 | 책임 | 함께 사는 데이터 |
|---|---|---|
| 견적 요청 (Request) | 고객이 낸 이사 요청 1건 | 출발/도착 주소·좌표, 이사 유형, 희망 일시, 짐 목록, 사진 |
| 견적 (Quote/Bid) | 파트너가 요청에 낸 제안 1건 | 금액, 포함 범위, 차량·인원, 유효 기한 |
| 예약 (Reservation) | 고객이 견적을 수락해 성립한 계약 | 확정 금액, 계약금·잔금, 안심예약 적용 여부 |
| 작업 (Job) | 실제 이사 수행 | 배차, 출발/완료 시각, 현장 변경 사항 |
| 정산 (Settlement) | 파트너 대금·수수료 | 수수료율, 정산 주기, 공제, 보류 |
| 리뷰 (Review) | 후기·평점 | 작성 자격, 신고, 노출 정책 |
| 분쟁 (Dispute) | 중재·보상 | 접수, 증빙, 처리 결과 |

**경계를 흐리면 바로 사고가 난다.** 특히 견적과 예약을 한 테이블에서 상태 컬럼으로만 구분하면,
"수락 후 견적 금액이 바뀌면 예약 금액도 바뀌는" 종류의 버그가 생긴다.
예약은 성립 시점의 견적 내용을 **스냅샷으로 복사해서** 들고 있어야 한다.
파트너가 나중에 자기 견적을 수정하거나 삭제해도 계약 내용은 남아야 하기 때문이다.

### 3.2 상태 기계

이 도메인의 본질은 트래픽이 아니라 **상태**다. 상태 전이를 문서로 고정하지 않으면 코드가 곧 무너진다.

```
견적 요청:  DRAFT → OPEN → QUOTED → MATCHED → CLOSED
                      ↘ EXPIRED   ↘ CANCELED

견적:      SUBMITTED → ACCEPTED → (예약 생성)
                    ↘ REJECTED
                    ↘ WITHDRAWN
                    ↘ EXPIRED

예약:      CONFIRMED → IN_PROGRESS → COMPLETED → SETTLED
                    ↘ CANCELED_BY_CUSTOMER
                    ↘ CANCELED_BY_PARTNER
                    ↘ NO_SHOW
```

설계 원칙 네 가지.

1. **현재 상태는 컬럼, 전이는 별도 이력 테이블.** `reservation.status`만 두면 "언제 누가 왜 취소했는지"가 사라진다.
   `reservation_status_history(reservation_id, from_status, to_status, reason, actor_type, actor_id, created_at)`를 함께 둔다.
   분쟁 중재 제도가 있는 서비스에서는 선택이 아니다.
2. **전이 규칙을 도메인 객체 안에 둔다.** 서비스 레이어 곳곳에서 `setStatus()`를 호출하면 규칙이 흩어진다.
   `reservation.cancel(reason, actor)` 같은 메서드가 불가능한 전이를 예외로 막아야 한다.
3. **취소는 상태가 아니라 사건이다.** 취소 시점(이사 3일 전 / 당일)에 따라 위약금이 달라진다.
   취소 정책은 상태 전이의 부수 효과가 아니라 독립된 계산 규칙으로 뺀다.
4. **시간에 의한 전이가 있다.** `EXPIRED`는 아무도 호출하지 않는데 일어난다.
   스케줄러가 만들거나, 조회 시점에 계산하거나 — 둘 중 하나를 정하고 섞지 않는다.

### 3.3 양면 시장이 만드는 문제

**최대 5개 견적 마감.** 파트너 여러 명이 동시에 견적을 낼 때 6번째가 끼어들면 안 된다.
DB 제약만으로는 못 막는다. 선택지는 셋이다.

- 비관적 락: 요청 행을 `SELECT ... FOR UPDATE`로 잡고 카운트 후 삽입. 단순하지만 요청 행에 경합이 몰린다.
- 낙관적 락: 요청에 `@Version`을 두고 견적 수 증가와 함께 갱신. 실패 시 재시도. 경합이 낮으면 유리하다.
- 유니크 제약: `unique(request_id, slot_no)` 로 슬롯을 미리 정의하고 슬롯을 선점하게 한다.
  중복 방지를 DB가 보증하지만 슬롯 관리가 늘어난다.

경합 빈도가 낮으면 낙관적 락, 인기 요청에 파트너가 몰리는 구조면 슬롯 방식이 안전하다.

**중복 배정.** 같은 파트너가 같은 시간대에 두 건을 잡으면 안 된다.
`unique(partner_id, moving_date, time_slot)` 같은 제약을 걸 수 있으면 걸고, 못 걸면 도메인 규칙으로 검증한다.
후자는 반드시 트랜잭션 안에서, 그리고 동시성 테스트로 검증해야 한다.

**파트너 노출 정책.** 어떤 파트너에게 어떤 요청을 보여줄지가 곧 비즈니스다.
지역, 상품 유형, 평점, 최근 노쇼 이력, 페널티, 정산 연체 여부가 필터가 된다.
이 조건이 늘어나면 쿼리가 감당을 못 한다. 노출 대상 계산을 **읽기 전용 모델로 분리**하거나
후보 파트너 목록을 미리 만들어두는 쪽으로 간다. (추정 — 규모에 따라 필요 시점이 다르다)

**노쇼와 취소.** 파트너 노쇼는 고객에게 회복 불가능한 피해다.
대체 파트너 재매칭, 알림, 보상까지 하나의 워크플로로 묶여야 한다.

### 3.4 이사 도메인 특유의 데이터

- **짐 목록.** 품목별 부피·무게가 견적의 근거다. 품목 마스터가 바뀌면 과거 견적의 재현이 깨진다.
  마스터를 버전으로 관리하거나, 견적에 품목 스냅샷을 남긴다.
- **사진.** 방 사진으로 견적을 낸다. 이미지 업로드·리사이즈·보관 기간·개인정보가 전부 걸린다.
  사진에는 집 내부와 얼굴이 찍힌다. 접근 통제와 만료 URL이 필요하다.
- **주소와 좌표.** 지오코딩 결과를 캐시하지 않으면 외부 API 비용과 지연이 그대로 들어온다.
  거리·소요시간은 견적 산정의 입력값이다. 직선거리와 실제 경로는 다르다.
- **건물 조건.** 층수, 엘리베이터 유무, 사다리차 필요 여부, 주차 가능 여부.
  이 값들이 금액을 크게 흔든다. `nullable` 로 방치하면 견적 로직이 조용히 틀린다.
- **날짜.** 이사 수요는 균등하지 않다. 주말, 월말, 손 없는 날에 몰린다.
  이건 **초당 요청 수 문제가 아니라 특정 날짜의 자원 경합 문제**다. 서버를 늘려도 파트너 수는 안 늘어난다.
  달력 단위 재고(capacity) 모델이 필요하다.

### 3.5 시간대와 날짜 처리

- 저장은 UTC, 표시는 KST — 이 원칙은 지키되, **이사 날짜는 시각이 아니라 날짜(LocalDate)** 다.
  `2026-03-14 00:00:00+09:00`으로 저장해두면 언젠가 하루가 밀린다.
- "이사 3일 전 취소" 같은 정책은 날짜 차이로 계산한다. 밀리초 차이로 계산하면 경계에서 틀린다.
- 성수기·공휴일·손 없는 날은 마스터 데이터다. 코드에 하드코딩하지 않는다.

## 4. RDB 설계 — 공고의 "테이블 설계"

### 4.1 스키마 원칙

- **정규화를 기본으로, 역정규화는 측정 후에.** 조회가 느리다는 이유로 먼저 컬럼을 복사하면
  갱신 누락으로 데이터가 갈라진다.
- **금액은 정수형.** 원 단위 `BIGINT` 또는 `DECIMAL`. `DOUBLE`은 쓰지 않는다.
  수수료율 계산에서 반올림 규칙(어느 자리에서, 어느 방향으로)을 명시하고 테스트한다.
- **감사 컬럼은 전 테이블 공통.** `created_at`, `updated_at`, `created_by`, `updated_by`.
  JPA에서는 `@MappedSuperclass` + `@EntityListeners(AuditingEntityListener.class)`로 묶는다.
- **삭제는 대체로 soft delete.** 다만 `deleted_at IS NULL` 조건이 모든 쿼리에 붙는 순간
  인덱스 설계가 복잡해진다. 정말 지워도 되는 테이블은 물리 삭제한다.
- **enum은 문자열로 저장.** `@Enumerated(EnumType.STRING)`. `ORDINAL`은 상수 순서가 바뀌면 데이터가 뒤섞인다.
  이건 JPA에서 가장 흔하고 가장 치명적인 실수다.
- **외래키를 걸 것인가.** 정합성은 얻고 배포·마이그레이션 유연성은 잃는다.
  회사 컨벤션을 먼저 확인할 항목이다.

### 4.2 인덱스

인덱스 질문은 면접에서 거의 확실히 나온다. 알아야 할 것.

- **B+Tree 구조**와 왜 범위 검색에 강한지.
- **복합 인덱스의 선두 컬럼 원칙.** `(a, b, c)` 인덱스는 `a`, `(a,b)`, `(a,b,c)` 조건에 쓰이고 `b`만으로는 안 쓰인다.
- **카디널리티.** 상태 컬럼처럼 값이 몇 개 안 되는 컬럼 단독 인덱스는 대체로 쓸모없다.
  단, `(status, created_at)` 처럼 정렬과 묶이면 유효하다.
- **커버링 인덱스.** 인덱스만으로 쿼리가 끝나면 테이블 접근이 사라진다. `EXPLAIN`의 `Using index`.
- **인덱스를 못 타게 만드는 것들.** 컬럼에 함수 적용(`DATE(created_at) = ...`), 앞부분 와일드카드 `LIKE '%x'`,
  묵시적 형변환(문자열 컬럼에 숫자 비교), `OR` 남용.
- **페이징.** `LIMIT 100000, 20`은 앞의 10만 행을 읽고 버린다.
  커서 기반(no-offset) `WHERE id < :lastId ORDER BY id DESC LIMIT 20`으로 바꾼다.
  이사 요청 목록처럼 계속 쌓이는 리스트에서 반드시 필요하다.

### 4.3 InnoDB와 트랜잭션

- **클러스터드 인덱스.** InnoDB는 PK 순서로 데이터를 저장한다.
  랜덤 UUID를 PK로 쓰면 삽입이 페이지 곳곳에 흩어져 성능이 떨어진다.
  외부 노출용 식별자가 필요하면 `AUTO_INCREMENT` PK + 별도 `public_id` 유니크 컬럼, 또는 정렬 가능한 UUIDv7.
- **격리 수준.** MySQL 기본은 REPEATABLE READ. 팬텀 리드를 갭 락으로 막는데,
  그 갭 락이 삽입을 막아 데드락의 원인이 되기도 한다. 견적 삽입 경합에서 실제로 만난다.
- **락 순서를 일정하게.** 여러 행을 갱신할 때 정렬된 순서로 잠그면 데드락이 크게 준다.
- **트랜잭션은 짧게.** 트랜잭션 안에서 외부 API를 호출하면 커넥션이 그 시간만큼 잡힌다.
  결제 호출, 알림 발송, 지오코딩은 트랜잭션 밖으로 뺀다. 이게 커넥션 풀 고갈의 1번 원인이다.
- **`@Transactional` 주의.** 프록시 기반이라 같은 클래스 내부 호출에는 안 걸린다.
  기본 롤백은 `RuntimeException`만. checked exception은 `rollbackFor` 지정이 필요하다.
  `readOnly = true`는 조회에서 더티체킹 비용을 없앤다.

### 4.4 NoSQL을 어디에 쓰나

공고가 NoSQL을 명시했지만, **모든 걸 NoSQL로 옮기는 게 아니라 용도를 나눌 줄 아는지**를 묻는 것에 가깝다. (추정)

| 용도 | 후보 | 이유 |
|---|---|---|
| 세션, 분산 락, 중복 요청 차단 | Redis | TTL과 원자 연산 |
| 조회수·랭킹·인기 파트너 | Redis (Sorted Set) | RDB 카운터 갱신 경합 회피 |
| 알림 발송 대기열 | Redis / SQS | 재시도와 DLQ |
| 견적 요청 스냅샷, 이력, 로그 | 문서 DB | 스키마가 상품 유형마다 다름 |
| 검색 | Elasticsearch | 형태소 분석, 다중 조건 |
| **주문·정산·금액** | **RDB** | 트랜잭션과 정합성이 우선 |

돈이 오가는 데이터는 RDB에 둔다. 이 선을 지키는지가 판단 기준이다.

## 5. JPA / Hibernate 딥다이브

공고가 "JPA 기반 서비스 2년 이상"을 못 박았다. 여기가 기술 검증의 중심일 가능성이 높다.

### 5.1 영속성 컨텍스트

- 1차 캐시, 동일성 보장, 쓰기 지연, 변경 감지(dirty checking).
- **더티체킹은 스냅샷 비교로 동작한다.** 조회한 엔티티의 필드를 바꾸면 `save()` 없이 UPDATE가 나간다.
  의도치 않은 수정이 나가는 사고가 여기서 생긴다.
- **flush 타이밍.** 트랜잭션 커밋 시, JPQL 실행 직전, 명시적 `flush()`.
  JPQL은 영속성 컨텍스트를 거치지 않고 DB로 가므로 그 전에 flush가 일어난다.
- **준영속(detached).** 트랜잭션 밖의 엔티티는 더티체킹이 안 된다. `merge()`의 동작(복사본 반환)을 정확히 알아야 한다.

### 5.2 N+1 — 처방과 각각의 한계

가장 자주 나오는 주제다. **원인을 한 문장으로 말할 수 있어야 한다.**
목록을 1번 조회하고, 각 행의 연관 엔티티를 프록시 초기화하며 N번 더 조회하는 것.

| 처방 | 쓰는 곳 | 한계 |
|---|---|---|
| `fetch join` | ToOne 연관, 컬렉션 1개 | **컬렉션 fetch join + 페이징은 메모리에서 페이징한다.** 하이버네이트가 경고를 남기고 전 행을 읽는다. 컬렉션 둘 이상은 `MultipleBagFetchException` |
| `@EntityGraph` | 선언적으로 같은 효과 | fetch join과 동일한 제약 |
| `hibernate.default_batch_fetch_size` | 컬렉션 + 페이징 조합 | 쿼리가 1+1로 줄 뿐 0이 되진 않음. 대신 페이징이 정상 동작 |
| DTO projection | 화면 전용 조회 | 엔티티가 아니므로 변경 감지 없음. 그게 오히려 장점 |
| `@BatchSize` | 특정 연관만 조절 | 전역 설정과 중복 관리 |

**실무 기본값:** ToOne은 fetch join, 컬렉션은 `default_batch_fetch_size`(100~1000), 목록 화면은 DTO 직접 조회.

### 5.3 OSIV

Spring Boot는 `spring.jpa.open-in-view`가 기본 `true`다.
영속성 컨텍스트를 뷰 렌더링까지 열어두므로 **DB 커넥션을 응답이 끝날 때까지 붙잡는다.**
외부 API 호출이 섞인 컨트롤러에서 커넥션 풀이 마른다.

끄는 게 맞다. 대신 지연 로딩이 트랜잭션 밖에서 터지므로,
서비스 레이어에서 필요한 데이터를 다 채워 DTO로 반환하는 구조가 강제된다. 그게 옳은 방향이다.

### 5.4 연관관계 매핑

- `@ManyToOne`, `@OneToOne`의 기본 fetch는 EAGER다. **전부 LAZY로 바꾼다.**
- **단방향을 기본으로.** 양방향은 연관관계 편의 메서드와 `mappedBy` 관리 비용을 만든다. 필요할 때만 연다.
- `cascade = ALL`, `orphanRemoval = true`는 **애그리게이트 루트와 그 부품 사이에서만.**
  예약이 파트너를 cascade 삭제하는 코드는 사고다.
- `@OneToOne` 양방향의 지연 로딩은 주인이 아닌 쪽에서 동작하지 않는다. 프록시를 만들 수 없기 때문이다.
- **`equals`/`hashCode`.** 엔티티에서 자동 생성한 걸 그대로 쓰면 LAZY 프록시와 비교할 때 깨진다.
  비즈니스 키나 ID 기준으로 직접 정의한다.

### 5.5 벌크 연산

`@Modifying` JPQL이나 네이티브 UPDATE는 영속성 컨텍스트를 건너뛴다.
실행 후 1차 캐시가 DB와 어긋난다. `clearAutomatically = true`를 주거나 벌크 연산을 트랜잭션 앞쪽에 배치한다.

대량 삽입은 JPA로 하지 않는다. `IDENTITY` 전략은 배치 삽입이 불가능하다(매번 INSERT 후 키를 받아야 함).
JDBC batch나 별도 경로로 뺀다.

### 5.6 복잡한 조회는 분리

목록·검색·통계는 엔티티 그래프로 풀지 않는다. QueryDSL이나 네이티브 쿼리로 **읽기 전용 모델**을 따로 둔다.
명령(쓰기)은 엔티티와 도메인 규칙으로, 조회는 DTO로 — 가벼운 CQRS다.
이 구분이 없으면 화면 요구사항이 엔티티 설계를 오염시킨다.

## 6. API 설계

### 6.1 자원 모델링과 상태 전이

REST에서 "예약 취소"를 어떻게 표현할지가 실전 문제다.
`PATCH /reservations/{id}` 에 `{"status": "CANCELED"}` 를 보내는 방식은
클라이언트가 상태 기계를 알아야 하고, 취소 사유 같은 부수 정보를 담기 어렵다.

실용적 타협은 행위를 하위 자원으로 두는 것이다.

```
POST /reservations/{id}/cancellation   { "reason": "...", "canceledBy": "CUSTOMER" }
POST /quotes/{id}/acceptance
```

순수한 REST는 아니지만 의도가 드러나고 권한 검사와 검증을 붙이기 쉽다. 이 트레이드오프를 설명할 수 있으면 된다.

### 6.2 멱등성

**결제와 예약 생성에 반드시 필요하다.** 모바일 앱은 네트워크가 끊기고, 사용자는 버튼을 두 번 누른다.

- 클라이언트가 `Idempotency-Key` 헤더로 UUID를 보낸다.
- 서버는 (키, 엔드포인트, 사용자) 조합을 유니크 제약이 걸린 테이블이나 Redis에 저장한다.
- 이미 있으면 저장된 응답을 그대로 돌려준다. 새로 처리하지 않는다.
- 처리 중인 상태도 구분해야 한다(진행 중이면 409 또는 대기).

이걸 "프론트에서 버튼 비활성화하면 됩니다"로 답하면 안 된다.

### 6.3 나머지 규격

- **에러 응답을 하나로.** 코드, 메시지, 필드 오류 목록. RFC 9457(Problem Details)을 참고할 수 있다.
  HTTP 상태 코드와 도메인 에러 코드를 분리한다.
- **페이지네이션.** 목록은 커서 기반을 기본으로. 총 개수(`count`)는 비싸므로 필요한 화면에만 준다.
- **버전 관리.** 앱은 강제 업데이트가 어렵다. **필드 추가만 허용하고 제거·의미 변경은 금지**가 현실적인 규칙이다.
  구버전 앱이 오래 남는다는 전제로 설계한다.
- **Spring Boot 4 / Framework 7**은 URL·헤더·미디어타입 기반 API 버저닝을 프레임워크 차원에서 지원한다.
- **응답에 내부 ID를 그대로 노출할지** 결정한다. `AUTO_INCREMENT` PK 노출은 규모와 경쟁사 정보를 흘린다.

## 7. 고가용성과 확장성

공고가 두 번 반복한 키워드다.

### 7.1 기본

- **무상태 서버.** 세션을 로컬 메모리에 두지 않는다. Redis 또는 토큰 기반.
- **그레이스풀 셧다운.** `server.shutdown=graceful`. 배포 중 처리 중인 요청을 끊지 않는다.
  스케줄러와 비동기 스레드 풀도 함께 정리한다.
- **헬스체크를 분리.** liveness(살아있음)와 readiness(트래픽 받을 준비)를 구분한다.
  DB가 죽었을 때 readiness만 내려야 재시작 루프에 빠지지 않는다.
- **단일 장애점 제거.** DB는 리더/레플리카, 읽기 분산. 다만 복제 지연으로 "방금 쓴 걸 못 읽는" 문제가 따라온다.
  쓰기 직후 조회는 리더로 보내는 라우팅이 필요하다.

### 7.2 캐시

- 로컬 캐시(Caffeine)는 빠르지만 인스턴스마다 다르다. 무효화가 안 된다.
- 분산 캐시(Redis)는 일관되지만 네트워크 왕복이 있다.
- **캐시 무효화가 본체다.** TTL만으로 버티는지, 이벤트로 지우는지 정한다.
- **캐시 스탬피드.** 인기 키가 동시에 만료되면 DB로 요청이 몰린다. TTL 지터, 논리적 만료, 뮤텍스로 막는다.
- **캐시 대상 선정.** 지오코딩 결과, 품목 마스터, 지역 코드처럼 **잘 안 바뀌고 자주 읽는 것**부터.
  견적 금액처럼 정확성이 중요한 값은 캐시하지 않는다.

### 7.3 비동기와 이벤트

이사 예약 하나가 확정되면 알림 발송, 파트너 통보, 통계 갱신, 외부 연동이 줄줄이 따라온다.
이걸 전부 동기로 처리하면 응답 시간이 외부 시스템에 인질로 잡힌다.

- **트랜잭션 커밋 후 발행.** Spring의 `@TransactionalEventListener(phase = AFTER_COMMIT)`.
  커밋 전에 발행하면 롤백된 예약의 알림이 나간다.
- **아웃박스 패턴.** DB 트랜잭션 안에 이벤트를 outbox 테이블에 함께 저장하고, 별도 프로세스가 읽어 발행한다.
  "DB는 커밋됐는데 메시지 발행이 실패"하는 구멍을 막는다.
- **소비자는 멱등해야 한다.** 메시지 큐는 대체로 at-least-once다. 같은 메시지가 두 번 온다고 전제한다.
- **재시도와 DLQ.** 지수 백오프, 최대 횟수, 실패 격리. 무한 재시도는 장애를 증폭시킨다.

### 7.4 알림 발송

이사 리마인더, 견적 도착, 파트너 배정 — 전부 알림이다. 푸시(FCM), 알림톡, SMS.

- 성수기 특정 날짜에 발송이 몰린다. 큐로 흡수하고 발송 속도를 제한한다.
- 외부 채널은 실패한다. 채널별 폴백(알림톡 실패 → SMS)과 발송 이력 테이블이 필요하다.
- 야간 발송 제한 같은 법적 제약이 있다. 예약 발송이 필요하다.

### 7.5 배치와 스케줄러

정산 마감, 견적 만료 처리, 리마인더, 통계 집계.

- **다중 인스턴스에서 스케줄러가 중복 실행된다.** ShedLock 같은 분산 락으로 한 번만 돌게 한다.
  `@Scheduled`를 그냥 쓰고 서버를 2대로 늘리면 정산이 두 번 나간다.
- **재실행 가능해야 한다.** 배치가 중간에 죽었을 때 처음부터 다시 돌려도 결과가 같아야 한다.
- **처리 구간을 기록한다.** "어제 것을 처리"가 아니라 "마지막 처리 지점 이후"로 잡는다.

## 8. 성능 최적화 — 순서를 지킬 것

공고에 "서비스의 성능을 위한 애플리케이션 최적화"가 명시돼 있다.
**추측으로 고치지 않는다**는 태도가 답의 절반이다.

1. **측정.** MySQL 슬로우 쿼리 로그, APM(Pinpoint / Scouter / Datadog), 액추에이터 메트릭.
   평균이 아니라 **p95·p99**를 본다. 평균은 최악의 사용자 경험을 숨긴다.
2. **병목 특정.** 응답 시간이 DB인지, 외부 API인지, GC인지, 락 대기인지.
3. **처방.**

| 증상 | 흔한 원인 | 처방 |
|---|---|---|
| 목록 API가 데이터 증가에 비례해 느려짐 | N+1 | fetch join / batch size / DTO 조회 |
| 특정 쿼리만 느림 | 인덱스 미사용 | `EXPLAIN` 확인, 복합 인덱스 추가 |
| 뒤 페이지로 갈수록 느림 | offset 페이징 | 커서 기반 전환 |
| 트래픽 늘면 전체가 멈춤 | 커넥션 풀 고갈 | 트랜잭션 단축, 외부 호출 분리, 풀 크기 조정 |
| 응답이 간헐적으로 튐 | GC / 외부 API 지연 | 힙 튜닝, 타임아웃·서킷브레이커 |
| CPU는 노는데 처리량이 안 늘어남 | 스레드 블로킹 | 비동기화, 풀 분리 |

- **HikariCP 풀 크기는 크게 잡을수록 좋은 게 아니다.** DB의 동시 처리 능력이 상한이다.
  풀이 크면 DB에서 대기가 생길 뿐이다. 시작점은 대체로 `(코어 수 × 2) + 유효 디스크 수` 수준이고, 측정으로 조정한다.
- **타임아웃을 전부 설정한다.** 커넥션, 읽기, 트랜잭션, HTTP 클라이언트.
  기본값이 무한대인 클라이언트가 장애를 전파한다.

## 9. 운영과 신뢰성

### 9.1 관측

- **구조화 로그 + 추적 ID.** 요청마다 traceId를 MDC에 넣고 모든 로그에 남긴다.
  분산 환경에서 이게 없으면 장애 분석이 불가능하다.
- **로그에 개인정보를 남기지 않는다.** 이 도메인은 주소와 연락처가 로그로 새기 쉽다. 마스킹을 기본으로.
- **비즈니스 지표를 모니터링한다.** CPU 말고 "시간당 견적 성립 수", "매칭 실패율".
  기술 지표가 정상인데 서비스가 죽어 있는 경우를 잡는 건 이쪽이다.

### 9.2 장애 격리

- 외부 연동(결제 PG, 지도 API, 알림 채널)은 반드시 실패한다.
  타임아웃 → 재시도(백오프) → 서킷브레이커 → 폴백 순으로 방어한다.
- **재시도가 장애를 키운다.** 느려진 시스템에 재시도를 퍼부으면 완전히 죽는다.
  재시도는 횟수 제한과 지터를 반드시 동반한다.

### 9.3 개인정보와 보안

이사 플랫폼의 데이터는 **집 주소, 연락처, 집 내부 사진, 이사 날짜**다.
"언제 그 집이 비는지"를 아는 데이터라는 점에서 민감도가 높다.

- 개인정보는 암호화 저장, 조회 권한 분리, 접근 로그.
- 보관 기간을 정하고 만료 삭제를 자동화한다.
- 사진은 서명된 만료 URL로만 접근하게 한다. 공개 버킷에 두지 않는다.
- 파트너에게 노출하는 고객 정보는 **매칭 성립 전에는 최소한으로.** 안심번호(050) 같은 중계 번호를 쓴다.
- 정보통신망법·개인정보보호법상 광고성 정보 수신 동의와 야간 발송 제한을 시스템에 반영한다.

### 9.4 돈의 정합성

- 결제·정산은 **모든 변동을 이력으로 남긴다.** 잔액을 덮어쓰지 않고 거래를 append 한다.
- PG사 데이터와 자체 데이터를 대사(reconciliation)하는 배치를 둔다. 불일치는 알림으로 띄운다.
- 부분 취소, 환불, 위약금 공제까지 상태로 표현한다.

## 10. 테스트

공고의 "요구사항 분석 및 테스트를 통한 RESTful API 구축"에 대응한다.

- **단위 테스트는 도메인 로직에.** 상태 전이 규칙, 금액 계산, 취소 정책 — 여기가 버그의 본진이다.
  스프링 컨텍스트 없이 순수 객체로 테스트되도록 설계하는 게 좋은 설계의 부산물이다.
- **슬라이스 테스트.** `@DataJpaTest`, `@WebMvcTest`로 필요한 부분만 띄운다. 전체 `@SpringBootTest`는 느리다.
- **Testcontainers.** H2로 테스트하면 MySQL 전용 문법과 락 동작을 못 잡는다.
  실제 MySQL 컨테이너로 돌리는 게 표준에 가깝다.
- **동시성 테스트.** 견적 5개 마감, 중복 배정 같은 규칙은 `CountDownLatch`로 동시 요청을 만들어 검증한다.
  단일 스레드 테스트만으로는 절대 안 잡힌다.
- **테스트 데이터.** 픽스처 빌더를 만든다. 엔티티가 복잡할수록 테스트 작성 비용이 커지고, 그러면 테스트를 안 쓰게 된다.

## 13. 점검 질문

각 항목에 스스로 답할 수 있는지로 준비 상태를 가늠할 수 있다.

**도메인**
- 견적과 예약을 왜 분리해야 하는가. 한 테이블로 두면 무엇이 깨지는가.
- 파트너 5명 견적 마감을 동시성 안전하게 구현하는 방법 세 가지와 각각의 트레이드오프는.
- 이사 3일 전 취소와 당일 취소를 다르게 처리하려면 어디에 로직을 두는가.
- 성수기 특정 날짜에 요청이 몰리는 문제는 서버 증설로 해결되는가.

**JPA**
- N+1의 원인을 한 문장으로. 컬렉션 fetch join에 페이징을 붙이면 무슨 일이 일어나는가.
- OSIV를 끄면 무엇이 좋아지고 무엇이 불편해지는가.
- 벌크 UPDATE 후 조회 결과가 이상한 이유는.
- `@Transactional`이 안 걸리는 대표적인 경우 두 가지는.

**DB**
- `(a, b, c)` 복합 인덱스가 안 쓰이는 쿼리 조건을 하나 들어보라.
- offset 페이징이 뒤로 갈수록 느린 이유와 대안은.
- UUID를 PK로 쓰면 InnoDB에서 왜 불리한가.
- 정산 금액을 `DOUBLE`로 저장하면 안 되는 이유는.

**시스템**
- 결제 API에 멱등성을 보장하는 구체적 방법은.
- 서버 2대로 늘렸더니 정산 배치가 두 번 돌았다. 원인과 해결은.
- 커밋 후 이벤트 발행을 써야 하는 이유와, 그래도 남는 구멍(아웃박스가 필요한 이유)은.
- 커넥션 풀을 늘렸는데 더 느려졌다. 가능한 원인은.

**태도**
- 최근에 발견해서 고친 시스템의 문제 하나를, 측정 → 원인 → 처방 → 검증 순으로 설명할 수 있는가.
  우대 사항이 정확히 이걸 묻는다.
