# 기술 블로그 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Astro로 만든 개발자 기술 블로그를 `sgom.github.io`에 배포하고, 이후 글쓰기가 규격대로 굴러가도록 템플릿과 `CLAUDE.md`까지 갖춘다.

**Architecture:** Astro Content Collections가 zod 스키마로 frontmatter를 강제하고, 빌드 시 정적 HTML을 생성한다. 목록·태그·시리즈 계산 로직은 `astro:content`에 의존하지 않는 순수 함수로 `src/lib/posts.ts`에 분리해 Vitest로 단위 테스트한다. 검색은 빌드 후 Pagefind가 정적 HTML을 훑어 인덱스를 만든다. `main` push 시 GitHub Actions가 빌드해 Pages에 배포한다.

**Tech Stack:** Astro 6, TypeScript, Vitest, Pagefind, `@astrojs/rss`, `@astrojs/sitemap`, GitHub Actions

## Global Constraints

- Node 24 (설치되어 있음: v24.15.0). 패키지 매니저는 npm (11.12.1).
- GitHub repo 이름은 `sGOM.github.io`. 계정은 `sGOM`.
- `astro.config.mjs`의 `site`는 `https://sgom.github.io`. **`base`는 설정하지 않는다** — 사용자 페이지 repo라 루트에 배포되므로 `base`를 넣으면 경로가 깨진다.
- 콘텐츠 디렉터리는 `src/content/posts/<slug>/index.md`. 이미지는 글과 같은 디렉터리에 둔다.
- Content collection 설정 파일 경로는 `src/content.config.ts` (`src/content/config.ts` 아님).
- 엔트리 식별자는 `entry.id`를 쓴다 (`entry.slug`는 구 API).
- 본문 렌더는 `import { render } from 'astro:content'` 후 `await render(entry)` (`entry.render()`는 구 API).
- 커밋 메시지는 한국어로 쓰고 `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`로 끝낸다.
- 글 본문의 말투 규칙(해요체, 과장 없음, 결론 먼저, 추측/사실 구분, 1인칭 생략 우선)은 콘텐츠에만 적용한다. 코드 주석과 UI 문구에는 적용하지 않는다.
- 설계 문서: `docs/superpowers/specs/2026-08-05-blog-design.md`
- **셸 명령은 Bash 도구로 실행한다.** 계획의 명령은 POSIX 문법(`rm -rf`, `mkdir -p`, heredoc)으로 적혀 있다. PowerShell 도구로 실행하면 파싱 오류가 난다.
- 개발 서버(`npm run dev`, `npm run preview`)는 `run_in_background`로 띄우고, 확인이 끝나면 종료한다. 포그라운드로 실행하면 세션이 막힌다.

const posts = defineCollection({
  loader: glob({
    pattern: '**/index.md',
    base: './src/content/posts',
    // 'hikari-pool-leak/index.md' -> 'hikari-pool-leak'
    generateId: ({ entry }) => entry.replace(/\/index\.md$/, ''),

      title: z.string(),
      description: z.string(),
      pubDate: z.coerce.date(),
      tags: z.array(z.string()).nonempty(),
      updatedDate: z.coerce.date().optional(),
      draft: z.boolean().default(false),
      series: z.string().optional(),
      seriesOrder: z.number().int().positive().optional(),

    .refine((d) => (d.series === undefined) === (d.seriesOrder === undefined), {

export const collections = { posts };

## 상황

주문 정산 배치를 돌리는 중에 애플리케이션이 주기적으로 멈췄습니다. 멈춘 동안에는 API 응답도 함께 지연됐고, 몇 분 뒤 저절로 회복됐습니다. 배치를 끄면 증상이 사라졌습니다.

## 증상

`HikariPool-1 - Connection is not available, request timed out after 30000ms` 예외가 5분 간격으로 반복됐습니다.

지표는 이랬습니다.

- 풀 최대 크기: 30
- 배치 동시 실행 수: 20
- `hikaricp_connections_pending`: 최대 12까지 상승 후 유지

산술적으로는 고갈될 수 없는 구조였습니다.

## 가설과 검증

> 가설 1: 배치가 아니라 API 트래픽이 풀을 쓰고 있다.

같은 시간대 API 요청 수를 확인했습니다. 평소와 차이가 없었고, 배치를 끄면 pending이 0이 됐습니다. 기각했습니다.

> 가설 2: 쿼리 하나가 느려 커넥션을 오래 붙잡고 있다.

슬로우 쿼리 로그를 봤습니다. 가장 느린 쿼리가 800ms였습니다. 타임아웃이 30초인 것을 생각하면 설명이 되지 않았습니다. 기각했습니다.

> 가설 3: 반납되지 않는 커넥션이 있다.

`hikaricp_connections_active`가 배치 시작 후 단조 증가하고 회복 시점까지 내려오지 않았습니다. 사용량이 아니라 누수의 모양이었습니다. `leakDetectionThreshold`를 10초로 설정하고 재현했습니다.

```
Connection leak detection triggered for conn0: ...
  at com.example.batch.SettlementReader.read(SettlementReader.java:58)
```

## 원인

`SettlementReader`가 `DataSource.getConnection()`을 직접 호출해 커서를 열고 있었습니다. 정상 경로에서는 `finally`에서 닫혔지만, 정산 대상이 없어 조기 반환하는 분기에서 닫지 않고 빠져나갔습니다.

배치 한 사이클마다 해당 분기를 타는 건이 몇 건씩 있었고, 그만큼 커넥션이 새어나갔습니다. 5분은 풀이 완전히 소진되기까지 걸린 시간이었습니다.

## 해결

`try-with-resources`로 감싸 모든 경로에서 반납되도록 바꿨습니다.

적용 후 `active`는 배치 중에도 8을 넘지 않았고 `pending`은 0을 유지했습니다.

## 배운 것

풀 크기와 동시성만 비교해 "고갈될 리 없다"고 판단한 것이 시간을 가장 많이 잡아먹었습니다. 사용량 문제와 누수 문제는 지표 모양이 다릅니다. `active`가 내려오지 않고 계속 오르면 사용량이 아니라 누수를 먼저 의심하는 편이 빠릅니다.

`leakDetectionThreshold`는 운영에서도 켜둘 만합니다. 스택 트레이스가 바로 범인을 가리킵니다.

## 왜 필요한가

같은 조회를 두 번 했는데 결과가 다르게 나오는 버그를 만나면, 격리 수준을 모르는 상태에서는 원인을 찾을 수 없습니다. 코드에는 아무 문제가 없기 때문입니다.

## 핵심 개념

격리 수준은 동시에 실행되는 트랜잭션이 서로를 얼마나 볼 수 있는지 정하는 설정입니다. 표준은 네 단계를 정의합니다.

| 수준 | 더티 리드 | 반복 불가능 읽기 | 팬텀 리드 |
|---|---|---|---|
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| READ COMMITTED | 방지 | 발생 | 발생 |
| REPEATABLE READ | 방지 | 방지 | 발생(표준상) |
| SERIALIZABLE | 방지 | 방지 | 방지 |

## 동작 원리

MySQL InnoDB는 REPEATABLE READ에서 MVCC로 스냅샷을 유지합니다. 트랜잭션이 처음 읽는 시점의 스냅샷을 계속 보므로, 다른 트랜잭션이 커밋해도 보이지 않습니다.

그래서 InnoDB의 REPEATABLE READ는 표준과 달리 일반 조회에서 팬텀 리드가 발생하지 않습니다. 다만 잠금을 거는 읽기(`SELECT ... FOR UPDATE`)는 스냅샷이 아니라 현재 데이터를 보기 때문에 이야기가 달라집니다.

## 직접 확인

세션 두 개를 열고 확인했습니다.

세션 A:

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT COUNT(*) FROM orders WHERE status = 'PENDING';
-- 결과: 3
```

세션 B:

```sql
INSERT INTO orders (status) VALUES ('PENDING');
COMMIT;
```

다시 세션 A:

```sql
SELECT COUNT(*) FROM orders WHERE status = 'PENDING';
-- 결과: 3  (스냅샷 유지)

SELECT COUNT(*) FROM orders WHERE status = 'PENDING' FOR UPDATE;
-- 결과: 4  (잠금 읽기는 현재 데이터)
```

같은 트랜잭션 안에서 같은 조건의 조회가 3과 4를 반환했습니다. 팬텀 리드를 재현한 것입니다.

## 언제 쓰고 언제 안 쓰나

MySQL 기본값인 REPEATABLE READ는 대부분의 애플리케이션에 적절합니다. 바꿀 이유가 없다면 두는 편이 낫습니다.

READ COMMITTED는 갭 락 범위가 좁아 잠금 경합이 줄어드는 것으로 알려져 있습니다. 쓰기 경합이 심한 시스템에서 검토할 만하지만, 반복 조회 결과가 달라질 수 있다는 점을 코드가 감당할 수 있어야 합니다.

SERIALIZABLE은 실무에서 쓰기 어렵습니다. 정합성이 절대적인 짧은 트랜잭션에 한정해 고려합니다.

주의할 점은 같은 REPEATABLE READ라도 DB마다 동작이 다르다는 것입니다. PostgreSQL은 InnoDB와 구현이 달라, 이 글의 결과를 그대로 옮길 수 없습니다.

export type PostLike = {
  id: string;
  data: {
    title: string;
    pubDate: Date;
    tags: string[];
    draft: boolean;
    series?: string;
    seriesOrder?: number;
  };
};

export function sortByDate<T extends PostLike>(posts: T[]): T[] {
  return [...posts].sort(
    (a, b) => b.data.pubDate.valueOf() - a.data.pubDate.valueOf()
  );
}

export function filterDrafts<T extends PostLike>(
  posts: T[],
  includeDrafts: boolean
): T[] {
  return includeDrafts ? posts : posts.filter((p) => !p.data.draft);
}

export function collectTags<T extends PostLike>(
  posts: T[]
): { tag: string; count: number }[] {
  const counts = new Map<string, number>();
  for (const p of posts) {
    for (const tag of p.data.tags) {
      counts.set(tag, (counts.get(tag) ?? 0) + 1);
    }
  }
  return [...counts.entries()]
    .map(([tag, count]) => ({ tag, count }))
    .sort((a, b) => b.count - a.count || a.tag.localeCompare(b.tag, 'ko'));
}

export function getSeriesPosts<T extends PostLike>(
  posts: T[],
  series: string
): T[] {
  return posts
    .filter((p) => p.data.series === series)
    .sort((a, b) => (a.data.seriesOrder ?? 0) - (b.data.seriesOrder ?? 0));
}

export function getSeriesNeighbors<T extends PostLike>(
  posts: T[],
  current: T
): { prev: T | null; next: T | null } {
  if (!current.data.series) return { prev: null, next: null };
  const ordered = getSeriesPosts(posts, current.data.series);
  const i = ordered.findIndex((p) => p.id === current.id);
  if (i === -1) return { prev: null, next: null };
  return {
    prev: ordered[i - 1] ?? null,
    next: ordered[i + 1] ?? null,
  };
}

export function collectSeries<T extends PostLike>(
  posts: T[]
): { name: string; count: number }[] {
  const counts = new Map<string, number>();
  for (const p of posts) {
    if (!p.data.series) continue;
    counts.set(p.data.series, (counts.get(p.data.series) ?? 0) + 1);
  }
  return [...counts.entries()]
    .map(([name, count]) => ({ name, count }))
    .sort((a, b) => a.name.localeCompare(b.name, 'ko'));
}
```

`src/content/posts/mvcc-snapshot/index.md`:

```markdown
---
title: MVCC 스냅샷은 언제 찍히나
description: REPEATABLE READ에서 스냅샷 생성 시점을 확인해봤습니다
pubDate: 2026-08-06
tags: ["Database", "MySQL", "트랜잭션"]
series: "트랜잭션 파헤치기"
seriesOrder: 2
---

## 왜 필요한가

`START TRANSACTION`을 실행한 시점에 스냅샷이 찍힌다고 알고 있으면, 트랜잭션을 열어둔 채 대기하다가 조회했을 때 예상과 다른 결과를 보게 됩니다.

## 핵심 개념

InnoDB의 일관된 읽기는 트랜잭션 시작이 아니라 **첫 번째 조회 시점**에 스냅샷을 만듭니다. `START TRANSACTION`만으로는 스냅샷이 생기지 않습니다.

## 동작 원리

InnoDB는 각 행에 트랜잭션 ID와 롤백 포인터를 함께 저장합니다. 조회가 처음 일어날 때 현재 활성 트랜잭션 목록을 읽어 read view를 만들고, 이후 조회는 이 read view를 기준으로 어떤 버전을 볼지 결정합니다.

read view가 만들어지기 전까지는 볼 기준이 없으므로, 트랜잭션을 열어두기만 한 상태에서는 스냅샷도 없습니다.

## 직접 확인

세션 A:

```sql
START TRANSACTION;
-- 아직 아무 조회도 하지 않음
```

세션 B:

```sql
INSERT INTO orders (status) VALUES ('PENDING');
COMMIT;
```

다시 세션 A:

```sql
SELECT COUNT(*) FROM orders WHERE status = 'PENDING';
-- 세션 B의 INSERT가 보인다
```

트랜잭션을 먼저 열었는데도 나중에 커밋된 행이 보였습니다. 스냅샷이 `START TRANSACTION`이 아니라 첫 조회에서 만들어졌기 때문입니다.

시작 시점에 고정하려면 명시해야 합니다.

```sql
START TRANSACTION WITH CONSISTENT SNAPSHOT;
```

이렇게 하면 같은 실험에서 세션 B의 INSERT가 보이지 않습니다.

## 언제 쓰고 언제 안 쓰나

일반적인 웹 요청에서는 트랜잭션을 열고 곧바로 조회하므로 두 시점의 차이가 드러나지 않습니다.

차이가 문제가 되는 것은 트랜잭션을 열어둔 채 외부 API를 호출하거나 사용자 입력을 기다리는 경우입니다. 다만 그런 구조라면 스냅샷 시점보다 트랜잭션을 오래 붙잡고 있다는 사실이 먼저 문제입니다.

여러 테이블을 한 시점 기준으로 읽어야 하는 리포트성 조회에는 `WITH CONSISTENT SNAPSHOT`이 유용합니다.

## 참고

- [MySQL 8.0 Reference Manual - Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)

import rss from '@astrojs/rss';
import { getCollection } from 'astro:content';
import { sortByDate, filterDrafts } from '../lib/posts';

export async function GET(context) {
  const all = await getCollection('posts');
  const posts = sortByDate(filterDrafts(all, false));

  return rss({
    title: 'sGOM',
    description: '개발하며 겪은 문제와 공부한 개념을 남깁니다',

      title: post.data.title,
      description: post.data.description,
      pubDate: post.data.pubDate,
      link: `/posts/${post.id}/`,
    })),

  });
}

```markdown
# 기술 블로그

개발하며 겪은 문제와 공부한 개념을 남기는 블로그. Astro로 만들어 GitHub Pages(`sgom.github.io`)에 배포한다.

## 글을 쓸 때

### 1. 템플릿 고르기

- **답을 모르는 상태에서 시작해 알아낸 글** → `templates/troubleshooting.md`
- **이미 답을 알고 정리하는 글** → `templates/concept.md`

애매하면 물어본다. 임의로 정하지 않는다.

### 2. 파일 위치

`src/content/posts/<영문-슬러그>/index.md`

이미지는 같은 디렉터리에 두고 `![설명](./이미지.png)`로 참조한다.
슬러그는 영문 소문자와 하이픈만 쓴다. URL이 `/posts/<슬러그>/`가 된다.

### 3. frontmatter

| 필드 | 필수 | 비고 |
|---|---|---|
| `title` | O | |
| `description` | O | 목록과 검색 결과에 노출된다 |
| `pubDate` | O | `2026-08-05` 형식 |
| `tags` | O | 최소 1개 |
| `updatedDate` | X | |
| `draft` | X | `true`면 개발 서버에서만 보인다 |
| `series` | X | `seriesOrder`와 반드시 함께 |
| `seriesOrder` | X | `series`와 반드시 함께. 1부터 |

`series`만 쓰고 `seriesOrder`를 빠뜨리면 빌드가 실패한다.

### 4. 말투

- **해요체(`~습니다`)로 고정.** 문단 안에서 `~죠`, `~고요` 정도의 변주는 허용한다.
- **감탄사와 과장을 쓰지 않는다.** (`대박`, `무려`, `충격적이게도`)
- **결론을 뒤로 미루지 않는다.** 문단 첫 문장에 요지를 놓는다.
- **추측과 사실을 표기로 구분한다.** (`~로 보입니다` vs `~였습니다`)
- **1인칭은 생략을 우선한다.** 필요할 때만 "저"를 쓴다.

이 규칙은 글 본문에만 적용한다. 코드 주석과 UI 문구에는 적용하지 않는다.
