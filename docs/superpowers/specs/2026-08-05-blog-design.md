# 개발자 기술 블로그 설계

작성일: 2026-08-05

## 목적

이직 포트폴리오로 쓸 개발자 기술 블로그를 만든다. 두 가지를 동시에 만족해야 한다.

1. **읽혀야 한다** — 채용 담당자와 면접관이 링크를 열었을 때 판단 근거가 되어야 한다.
2. **오래 남아야 한다** — 겪은 문제와 공부한 개념이 자산으로 축적되어야 한다.

주된 글감은 실무에서 겪은 어려운 문제와, 공부한 개념이다.

## 플랫폼: GitHub Pages + Astro

### 결정

Astro로 정적 사이트를 만들어 GitHub Pages(`sGOM.github.io`)에 배포한다.

### 검토한 대안

| 안 | 내용 | 판단 |
|---|---|---|
| A | velog 단독 | 초기 노출은 가장 빠르나 글이 플랫폼에 종속된다 |
| B | GitHub Pages 단독 | **채택.** 소유권과 구조 통제를 전부 가져간다 |
| C | 마크다운 원본은 git, 발행은 velog | 기각 |

C를 기각한 이유는 중간 지대의 비용 때문이다. 원본과 발행본이 갈라지는 순간 어느 쪽이 진실인지 모호해지고, 그 동기화 비용을 지불하면서 B의 이점(도메인, 구조 통제)은 얻지 못한다. "C를 할 바에는 B, C가 아니라면 A"가 옳은 판단이다.

B가 A보다 나은 이유는 Claude Code가 사이트 구축을 대신할 수 있어 B의 최대 단점인 초기 구축 비용이 사라지기 때문이다. 이 조건이 아니었다면 A가 합리적이었다.

### SSG 선택 근거

Astro를 선택했다. 마크다운/MDX 처리가 가장 깔끔하고, Node 24가 이미 설치되어 있어 추가 런타임이 필요 없다. Hugo는 Go 템플릿 문법이 직접 수정할 때 진입 장벽이 되고, Jekyll은 Windows에서 Ruby 환경 구성이 번거롭다.

### B의 알려진 위험

유입이 0인 상태로 시작하므로 반응이 없어 글쓰기가 중단될 수 있다. 이를 완화하기 위해 SEO 기본기(sitemap, RSS, OG 이미지, 시맨틱 마크업)를 초기 구축에 포함한다.

## 말투: 담담한 해요체

### 규칙

- 해요체(`~습니다`)로 고정한다. 문단 안에서 `~죠`, `~고요` 정도의 변주는 허용한다.
- 감탄사와 과장을 쓰지 않는다. (`대박`, `무려`, `충격적이게도`)
- 결론을 뒤로 미루지 않는다. 문단 첫 문장에 요지를 놓는다.
- 추측과 사실을 표기로 구분한다. (`~로 보입니다` vs `~였습니다`)
- 1인칭은 생략을 우선한다. 필요할 때만 "저"를 쓴다.

### 근거

포트폴리오 용도에서 가장 위험이 낮고, 글이 길어져도 읽는 부담이 적다. 구어체 대화형은 velog에서 흔하지만 분량이 늘면 산만해지고, 드라이한 기술문체는 개인 경험이 드러나지 않아 이 블로그의 차별점을 지운다.

## 템플릿: 2종

글 목적이 다르면 뼈대도 달라야 하므로 두 개로 분리한다.

### 템플릿 1 — 문제해결형 (`templates/troubleshooting.md`)

```markdown
---
title:
description:
pubDate:
tags: []
---

## 상황
어떤 시스템에서, 무엇을 하다가 마주쳤는지. 3~4문장.

## 증상
관측된 사실만. 로그, 지표, 에러 메시지. 추측은 쓰지 않는다.

## 가설과 검증
> 가설 1: ○○일 것이다

무엇을 근거로 세웠고, 어떻게 확인했고, 결과가 무엇이었는지.
틀린 가설도 남긴다.

## 원인
왜 그런 일이 일어났는지. 코드/설정 수준의 근거와 함께.

## 해결
바꾼 것과, 바꾼 뒤 지표가 어떻게 변했는지.

## 배운 것
다음에 비슷한 상황에서 무엇을 먼저 볼 것인가. 2~3줄.
```

**"가설과 검증"에 틀린 가설을 남기는 것이 이 템플릿의 존재 이유다.** 정답만 적힌 글은 검색 결과와 구별되지 않는다. 어떻게 좁혀갔는지가 남아야 대체 불가능한 글이 되고, 면접에서 그대로 말할 거리가 된다.

### 템플릿 2 — 개념학습형 (`templates/concept.md`)

```markdown
---
title:
description:
pubDate:
tags: []
---

## 왜 필요한가
이 개념을 모르면 어떤 문제를 겪는지. 정의부터 시작하지 않는다.

## 핵심 개념
최소한의 정의. 길어지면 글의 목적이 흐려진다.

## 동작 원리
내부적으로 어떻게 돌아가는지. 그림이나 순서도.

## 직접 확인
코드로 재현. 실행 결과 포함.

## 언제 쓰고 언제 안 쓰나
트레이드오프. 실무에서의 판단 기준.

## 참고
출처 링크.
```

**"직접 확인" 섹션이 정리 노트와 블로그 글을 가른다.** 공식 문서를 요약한 글은 이미 많지만 직접 재현해 확인한 글은 적다. 이 섹션이 비면 글을 발행하지 않는다.

### 템플릿 선택 기준

- 이미 답을 알고 시작한 글 → 개념학습형
- 답을 모르는 상태에서 시작해 알아낸 글 → 문제해결형

## 콘텐츠 원칙

**회사 실무 경험담은 쓰지 않는다.** 면접 준비 자료에 정리된 STAR 세트(조회 결과 불일치, 권한 검증 분리, 레거시 역추적)는 블로그 소재에서 제외한다. 특정 회사·제품·시스템 이름이 본문에 등장해서는 안 된다.

**없는 사실을 만들지 않는다.** 겪지 않은 트러블슈팅, 실행하지 않은 결과, 극적 효과를 위한 수치나 로그를 지어내지 않는다. 포트폴리오 용도에서 이것이 드러나면 글이 쌓인 것보다 큰 손해다.

초기 글감은 공부한 CS 개념이며, 개인 저장소 [`spring-transactional-test`](https://github.com/sGOM/spring-transactional-test)(SpringBoot + H2 + Kotlin + Kotest)의 실제 테스트 코드를 "직접 확인" 섹션의 근거로 쓴다. 회사 코드가 아니라 공개된 본인 저장소이므로 인용에 제약이 없고, 개념학습형 템플릿이 요구하는 재현 코드를 실제로 갖추고 있다.

## 저장소 구성

```
blog/
├── src/
│   ├── content/posts/
│   │   └── <slug>/
│   │       ├── index.md
│   │       └── *.png          # 이미지는 글과 같은 디렉터리에
│   ├── layouts/
│   ├── components/
│   ├── pages/
│   └── styles/
├── templates/
│   ├── troubleshooting.md
│   └── concept.md
├── docs/superpowers/specs/
├── CLAUDE.md
├── astro.config.mjs
└── .github/workflows/deploy.yml
```

### CLAUDE.md

이 설계에서 가장 중요한 파일이다. 말투 규칙과 템플릿 선택 기준을 여기에 적어두면, 이후 세션에서 "이런 문제를 겪었다"고만 말해도 규격에 맞는 초고가 나온다. 결정 사항이 읽고 잊는 문서가 아니라 매번 적용되는 규칙이 된다.

담을 내용은 말투 규칙 5항, 템플릿 2종의 위치와 선택 기준, frontmatter 스키마, 글 작성 워크플로다.

## 콘텐츠 스키마

Astro Content Collections와 zod로 frontmatter를 강제한다.

| 필드 | 타입 | 필수 |
|---|---|---|
| `title` | string | O |
| `description` | string | O |
| `pubDate` | date | O |
| `tags` | string[] | O |
| `updatedDate` | date | X |
| `draft` | boolean | X (기본 false) |
| `series` | string | X |
| `seriesOrder` | number | X (`series`가 있으면 필수) |

필수 필드가 누락되면 빌드가 실패한다. 규격이 문서가 아니라 빌드로 강제된다.

`series`와 `seriesOrder`는 zod `refine`으로 함께 있거나 함께 없도록 강제한다. 시리즈 이름만 적고 순서를 빠뜨리면 빌드가 실패한다.

## 페이지

| 경로 | 내용 |
|---|---|
| `/` | 글 목록 |
| `/posts/[slug]` | 본문 |
| `/tags/[tag]` | 태그별 목록 |
| `/series/[name]` | 시리즈별 목록 |
| `/search` | 검색 |
| `/about` | 소개 |
| `/rss.xml` | RSS |

`/about`은 포트폴리오 용도상 우선순위가 높다. 이력과 GitHub 링크를 담는다.

`draft: true`인 글은 프로덕션 빌드에서 제외하되 로컬 개발 서버에서는 보이게 한다.

## 디자인

기성 테마를 쓰지 않고 직접 구성한다. 테마는 대개 이 블로그에 필요 없는 기능을 함께 끌고 오고, 나중에 고치려 할 때 오히려 걸림돌이 된다.

기준은 읽기 편함이다.

- 본문 한 줄은 한글 기준 40자 안팎으로 제한한다.
- 시스템 폰트를 쓴다. 웹폰트를 받느라 첫 렌더가 밀리지 않게 한다.
- 다크모드를 지원하고, 시스템 설정을 따르되 토글로 덮어쓸 수 있게 한다.
- 코드 블록은 모바일에서 가로 스크롤한다. 페이지 전체가 가로로 밀리면 안 된다.
- 색은 최소한으로 쓴다. 강조색 하나와 무채색 계열로 끝낸다.

구현 중에 목록 페이지와 본문 페이지 시안을 브라우저로 띄워 확인받는다. 문장으로 합의하기 어려운 영역이므로 보고 고르는 편이 빠르다.

## 검색

Pagefind를 쓴다. 빌드가 끝난 정적 HTML을 훑어 인덱스를 만들고, 검색은 전부 브라우저에서 처리한다. 서버나 외부 서비스가 필요 없어 GitHub Pages에 그대로 올라간다.

빌드 스크립트를 `astro build && pagefind --site dist`로 구성한다. Astro 빌드 산출물에 인덱스를 덧붙이는 방식이라 콘텐츠가 늘어도 별도 관리가 없다.

**한국어 관련 제약:** Pagefind는 형태소 분석을 하지 않아 조사가 붙은 어절("커넥션이", "커넥션을")을 같은 단어로 묶지 못한다. 명사 검색은 잘 동작하지만 완전한 한국어 검색은 아니다. 대안인 Fuse.js는 인덱스를 직접 만들고 전체를 클라이언트로 내려받아야 해서 글이 늘수록 비용이 커진다. 이 트레이드오프를 받아들이고 Pagefind로 간다.

## 시리즈

`series`(시리즈 이름)와 `seriesOrder`(순서)로 글을 묶는다. 별도 정의 파일 없이 frontmatter만으로 시리즈가 생기고, 나중에 글을 끼워 넣을 때 순서 번호만 조정하면 된다.

- `/series/[name]`에서 해당 시리즈 글을 `seriesOrder` 순으로 나열한다.
- 본문 상단에 시리즈 목차를 접힌 상태로 넣고, 현재 글을 강조한다.
- 본문 하단에 이전 글/다음 글 링크를 넣는다.

시리즈에 속한 글도 `/` 목록과 태그 페이지에 평소처럼 나온다. 시리즈는 분류가 아니라 읽는 순서를 알려주는 장치다.

## 배포

repo 이름은 `sGOM.github.io`로 한다. `sgom.github.io/`가 루트가 되어 주소가 깔끔하고, 커스텀 도메인을 나중에 붙일 때도 단순하다.

`main`에 push하면 GitHub Actions가 빌드해 Pages에 배포한다.

**알려진 제약:** 현재 gh 토큰 스코프는 `gist`, `read:org`, `repo`로 `workflow`가 없다. git push가 SSH로 설정되어 있어 워크플로 파일 push가 성공할 가능성이 높지만, 실패하면 사용자가 `gh auth refresh -s workflow`를 직접 실행해야 한다.

## 이번 범위에서 제외한 것

| 항목 | 이유 |
|---|---|
| 댓글(giscus) | 글이 없는 상태에서 댓글창부터 만들 이유가 없다. 글이 쌓인 뒤 추가한다 |
| 조회수 | 정적 사이트에서는 외부 서비스가 필요하다. 지금 필요하지 않다 |
| 커스텀 도메인 | 언제든 얹을 수 있다 |

## 완료 조건

1. `sgom.github.io`가 실제로 열리고 글 목록이 보인다.
2. 개념학습형 글 3편이 시리즈로 묶여 렌더링된다. 문제해결형 템플릿은 파일로 제공되고 빌드로 검증된다.
3. 로컬에서 `npm run dev`로 미리보기가 되고, push하면 자동 배포된다.
4. `CLAUDE.md`만 읽고도 다음 세션에서 규격에 맞는 초고를 쓸 수 있다.
5. 다크모드가 동작하고 모바일에서 코드 블록이 가로 스크롤된다.
6. `/search`에서 글 제목과 본문의 명사가 검색된다.
7. 같은 `series`를 가진 글 2편이 `/series/[name]`에 순서대로 나오고, 본문에서 서로 이동된다.
