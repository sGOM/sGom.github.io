# 기술 블로그 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Astro로 만든 개발자 기술 블로그를 `sgom.github.io`에 배포하고, 이후 글쓰기가 규격대로 굴러가도록 템플릿과 `CLAUDE.md`까지 갖춘다.

**Architecture:** Astro Content Collections가 zod 스키마로 frontmatter를 강제하고, 빌드 시 정적 HTML을 생성한다. 목록·태그·시리즈 계산 로직은 `astro:content`에 의존하지 않는 순수 함수로 `src/lib/posts.ts`에 분리해 Vitest로 단위 테스트한다. 검색은 빌드 후 Pagefind가 정적 HTML을 훑어 인덱스를 만든다. `main` push 시 GitHub Actions가 빌드해 Pages에 배포한다.

**Tech Stack:** Astro 6, TypeScript, Vitest, Pagefind, `@astrojs/rss`, `@astrojs/sitemap`, GitHub Actions

## Global Constraints

- Node 24 (설치되어 있음: v24.15.0). 패키지 매니저는 npm (11.12.1).
- GitHub repo는 **이미 존재하는** `sGOM/sGom.github.io`(2018년 생성). 새로 만들지 않는다. 기존 `master` 브랜치의 옛 파일은 건드리지 않고, 블로그는 새 `main` 브랜치로 올린 뒤 기본 브랜치를 `main`으로 바꾼다.
- `astro.config.mjs`의 `site`는 `https://sgom.github.io`. **`base`는 설정하지 않는다** — 사용자 페이지 repo라 루트에 배포되므로 `base`를 넣으면 경로가 깨진다.
- 콘텐츠 디렉터리는 `src/content/posts/<slug>/index.md`. 이미지는 글과 같은 디렉터리에 둔다.
- Content collection 설정 파일 경로는 `src/content.config.ts` (`src/content/config.ts` 아님).
- 엔트리 식별자는 `entry.id`를 쓴다 (`entry.slug`는 구 API).
- 본문 렌더는 `import { render } from 'astro:content'` 후 `await render(entry)` (`entry.render()`는 구 API).
- 커밋 메시지는 한국어로 쓰고 `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`로 끝낸다.
- 글 본문의 말투 규칙(해요체, 과장 없음, 결론 먼저, 추측/사실 구분, 1인칭 생략 우선)은 콘텐츠에만 적용한다. 코드 주석과 UI 문구에는 적용하지 않는다.
- 설계 문서: `docs/superpowers/specs/2026-08-05-blog-design.md`
- **셸 명령은 Bash 도구로 실행한다.** 계획의 명령은 POSIX 문법(`rm -rf`, `mkdir -p`, heredoc)으로 적혀 있다. PowerShell 도구로 실행하면 파싱 오류가 난다.
- 개발 서버(`npm run dev`, `npm run preview`)는 `run_in_background`로 띄우고, 확인이 끝나면 종료한다. 포그라운드로 실행하면 세션이 막힌다.

- [ ] **Step 4: 배포 워크플로 작성**

`.github/workflows/deploy.yml`:

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v7
      - name: Build
        uses: withastro/action@v6

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v5
```

`sGOM/sGom.github.io`는 **2018년부터 존재하는 저장소**다. 새로 만들지 않는다. `gh repo create`를 실행하면 실패한다.

### Task 2: 콘텐츠 스키마와 예시 글

**Files:**
- Create: `src/content.config.ts`
- Create: `src/content/posts/transaction-isolation-levels/index.md`
- Create: `src/content/posts/transactional-propagation/index.md`

**콘텐츠 원칙 (이 태스크에서 가장 중요):**

두 글 모두 **개념학습형**이며, 소재는 사용자가 면접 준비 자료 §4에 이미 정리해둔 CS 개념이다.

- **실무 경험담을 쓰지 않는다.** 사용자가 명시적으로 제외했다. 회사에서 겪은 문제, 프로젝트 이야기, 특정 회사·제품·시스템 이름이 본문에 등장하면 안 된다.
- **없는 사실을 만들지 않는다.** 본문에 적힌 개념 설명과 DBMS 동작은 공식 문서로 확인되는 표준 동작이다. 극적 효과를 위한 수치, 로그, 일화를 덧붙이지 않는다.
- 코드는 누구나 재현할 수 있는 최소 예시다.

`draft`는 지정하지 않는다(기본값 `false`). 초안으로 두면 프로덕션 빌드에서 제외되어 검색 인덱스와 시리즈 페이지를 검증할 수 없기 때문이다.

대신 **Task 13에서 실제 배포 전에 사용자가 글 세 편을 검토하는 단계를 거친다.** 그 자리에서 내용이 사실과 다르거나 더 다듬어야 하면 `draft: true`를 붙여 배포에서 뺀다. 이 태스크의 구현자는 그 판단을 대신하지 않는다.

문제해결형 템플릿의 예시 글은 이 태스크에서 만들지 않는다. 소재가 실무 경험뿐인데 그건 제외됐다. 템플릿 파일 자체는 Task 12에서 만들고 빌드로 검증한다.

**Interfaces:**
- Consumes: Task 1의 Astro 프로젝트
- Produces: `posts` 컬렉션. 엔트리 `data`는 `{ title: string; description: string; pubDate: Date; tags: string[]; updatedDate?: Date; draft: boolean; series?: string; seriesOrder?: number }`. 엔트리 `id`는 디렉터리 이름(예: `transaction-isolation-levels`).

- [ ] **Step 1: 스키마 작성**

`src/content.config.ts`:

```ts
import { defineCollection } from 'astro:content';
import { glob } from 'astro/loaders';
import { z } from 'astro/zod';

const posts = defineCollection({
  loader: glob({
    pattern: '**/index.md',
    base: './src/content/posts',
    // 'transaction-isolation-levels/index.md' -> 'transaction-isolation-levels'
    generateId: ({ entry }) => entry.replace(/\/index\.md$/, ''),
  }),
  schema: z
    .object({
      title: z.string(),
      description: z.string(),
      pubDate: z.coerce.date(),
      tags: z.array(z.string()).nonempty(),
      updatedDate: z.coerce.date().optional(),
      draft: z.boolean().default(false),
      series: z.string().optional(),
      seriesOrder: z.number().int().positive().optional(),
    })
    .refine((d) => (d.series === undefined) === (d.seriesOrder === undefined), {
      message: 'series와 seriesOrder는 함께 있거나 함께 없어야 합니다',
    }),
});

export const collections = { posts };
```

- [ ] **Step 5: 격리 수준 글 작성**

`src/content/posts/transaction-isolation-levels/index.md`

frontmatter는 정확히 아래와 같이 쓴다.

```yaml
---
title: 트랜잭션 격리 수준은 DBMS마다 다르게 동작합니다
description: 표준 정의만 외우면 실무에서 틀리는 이유와, 테스트로 직접 확인한 기록
pubDate: 2026-08-05
tags: ["Database", "트랜잭션", "테스트"]
---
```

본문은 개념학습형 템플릿 구조를 따르고, 각 섹션에 아래 내용을 담는다. 말투 규칙(해요체, 과장 없음, 결론 먼저)을 지킨다.

| 섹션 | 담을 내용 |
|---|---|
| `## 왜 필요한가` | 같은 조회를 두 번 했는데 결과가 다른 상황. 코드에는 문제가 없어서, 격리 수준을 모르면 원인을 찾을 수 없다는 점 |
| `## 핵심 개념` | 격리 수준 4단계와 이상 현상 3종(Dirty Read / Non-Repeatable Read / Phantom Read)을 표로. 각 이상 현상의 정의는 한 줄씩 |
| `## 동작 원리` | **이 글의 핵심.** 표의 값은 표준 정의일 뿐이고 실제 DBMS는 다르게 동작한다. MySQL InnoDB는 기본이 REPEATABLE READ이고 잠금 읽기에서 갭 락·넥스트키 락으로 팬텀을 상당 부분 막는다. PostgreSQL은 기본이 READ COMMITTED이고 MVCC 기반이라 읽기가 쓰기를 막지 않으며, REPEATABLE READ는 스냅샷 격리라 팬텀이 안 생기는 대신 충돌 시 직렬화 실패로 트랜잭션이 죽어 재시도가 필요하다 |
| `## 직접 확인` | Step 4에서 읽은 `IsolationLevelTest.kt`에서 핵심 테스트 하나를 발췌. H2 환경이라는 점을 명시하고, 무엇을 검증하는 테스트인지 코드 위에 한두 문장으로 설명. 아래에 저장소 링크 |
| `## 언제 쓰고 언제 안 쓰나` | 기본값을 바꿀 이유가 없으면 두는 편이 낫다. READ COMMITTED는 잠금 경합이 줄지만 반복 조회 결과가 달라질 수 있어 코드가 감당해야 한다. SERIALIZABLE은 정합성이 절대적인 짧은 트랜잭션에 한정. 무엇보다 **어떤 DBMS를 쓰는지 확인하는 것이 표를 외우는 것보다 먼저다** |

```ts
export type PostLike = {
  id: string;
  data: {
    title: string;
    pubDate: Date;
    tags: string[];
    draft: boolean;
    series?: string;
    seriesOrder?: number;
  };
};

export function sortByDate<T extends PostLike>(posts: T[]): T[] {
  return [...posts].sort(
    (a, b) => b.data.pubDate.valueOf() - a.data.pubDate.valueOf()
  );
}

export function filterDrafts<T extends PostLike>(
  posts: T[],
  includeDrafts: boolean
): T[] {
  return includeDrafts ? posts : posts.filter((p) => !p.data.draft);
}

export function collectTags<T extends PostLike>(
  posts: T[]
): { tag: string; count: number }[] {
  const counts = new Map<string, number>();
  for (const p of posts) {
    for (const tag of p.data.tags) {
      counts.set(tag, (counts.get(tag) ?? 0) + 1);
    }
  }
  return [...counts.entries()]
    .map(([tag, count]) => ({ tag, count }))
    .sort((a, b) => b.count - a.count || a.tag.localeCompare(b.tag, 'ko'));
}

export function getSeriesPosts<T extends PostLike>(
  posts: T[],
  series: string
): T[] {
  return posts
    .filter((p) => p.data.series === series)
    .sort((a, b) => (a.data.seriesOrder ?? 0) - (b.data.seriesOrder ?? 0));
}

export function getSeriesNeighbors<T extends PostLike>(
  posts: T[],
  current: T
): { prev: T | null; next: T | null } {
  if (!current.data.series) return { prev: null, next: null };
  const ordered = getSeriesPosts(posts, current.data.series);
  const i = ordered.findIndex((p) => p.id === current.id);
  if (i === -1) return { prev: null, next: null };
  return {
    prev: ordered[i - 1] ?? null,
    next: ordered[i + 1] ?? null,
  };
}

export function collectSeries<T extends PostLike>(
  posts: T[]
): { name: string; count: number }[] {
  const counts = new Map<string, number>();
  for (const p of posts) {
    if (!p.data.series) continue;
    counts.set(p.data.series, (counts.get(p.data.series) ?? 0) + 1);
  }
  return [...counts.entries()]
    .map(([name, count]) => ({ name, count }))
    .sort((a, b) => a.name.localeCompare(b.name, 'ko'));
}
```


frontmatter는 정확히 아래와 같이 쓴다.

```yaml
---
title: 같은 클래스 안에서 부른 @Transactional은 왜 동작하지 않을까
description: Spring AOP의 프록시 기반 동작을 테스트로 확인했습니다
pubDate: 2026-08-07
tags: ["Spring", "트랜잭션", "AOP"]
series: "트랜잭션을 테스트로 확인하기"
seriesOrder: 3

```

본문은 개념학습형 템플릿 구조를 따르고, 각 섹션에 아래 내용을 담는다.

| 섹션 | 담을 내용 |
|---|---|
| `## 왜 필요한가` | `@Transactional`을 분명히 붙였는데 롤백이 되지 않는 상황. 어노테이션이 있으니 코드만 봐서는 원인이 보이지 않는다 |
| `## 핵심 개념` | Spring AOP는 프록시 기반이다. 빈을 주입받을 때 실제 객체가 아니라 프록시를 받고, 트랜잭션 처리는 그 프록시가 담당한다 |
| `## 동작 원리` | 외부에서 빈의 메서드를 호출하면 프록시를 거치므로 트랜잭션이 시작된다. 반면 같은 클래스 안에서 `this.method()`로 부르면 프록시를 거치지 않고 원본 객체의 메서드가 곧바로 실행되어 어노테이션이 무시된다. 해결 방법으로는 별도 빈으로 분리하는 것, 자기 자신을 주입받는 것, `TransactionTemplate`을 쓰는 것이 있고 **분리가 가장 단순하다** |
| `## 직접 확인` | 위에서 읽은 `SelfInvocationTest.kt`에서 핵심 케이스를 발췌. 외부 호출과 내부 호출의 결과가 갈리는 대비가 드러나야 한다. 아래에 저장소 링크 |
| `## 언제 쓰고 언제 안 쓰나` | 이 함정은 `@Transactional`뿐 아니라 프록시 기반 AOP 전체에 적용된다(`@Async`, `@Cacheable` 등). 어노테이션이 붙은 메서드를 같은 클래스에서 부르고 있다면 일단 의심한다 |

```js
import { getCollection } from 'astro:content';
import { sortByDate, filterDrafts } from '../lib/posts';

export async function GET(context) {
  const all = await getCollection('posts');
  const posts = sortByDate(filterDrafts(all, false));
```

개발하며 겪은 문제와 공부한 개념을 남기는 블로그. Astro로 만들어 GitHub Pages(`sgom.github.io`)에 배포한다.

### 1. 템플릿 고르기

| 필드 | 필수 | 비고 |
|---|---|---|
| `title` | O | |
| `description` | O | 목록과 검색 결과에 노출된다 |
| `pubDate` | O | `2026-08-05` 형식 |

브라우저 너비를 375px로 줄이고 확인한다.

1. 가로 스크롤이 생기지 않는다.
2. 코드 블록과 표만 각자 가로 스크롤된다.
3. 테마 토글이 동작하고 새로고침 후에도 유지된다.
4. 다크모드에서 코드 블록 색이 바뀐다.

- [ ] **Step 4: 사용자에게 글 3편 검토받기 (배포 전 필수)**

여기서 처음으로 글이 공개된다. push 전에 반드시 멈추고 사용자에게 확인받는다.

사용자에게 다음을 요청한다.

1. 글 세 편(`/posts/transaction-isolation-levels/`, `/posts/transactional-propagation/`, `/posts/transactional-self-invocation/`)을 읽어볼 것
2. 특히 **"직접 확인" 섹션의 코드와 설명이 실제 저장소 테스트의 동작과 맞는지** 확인할 것 — 이 부분은 저장소를 직접 돌려본 사용자만 판단할 수 있다
3. 사실과 다르거나 더 다듬어야 하는 글이 있으면 알려줄 것

사용자가 특정 글을 보류하겠다고 하면 해당 글의 frontmatter에 `draft: true`를 추가하고 커밋한다. 세 편 모두 보류되면 홈이 빈 목록이 되는데, 그것도 정상 동작이므로 그대로 배포한다.

**사용자 응답 없이 Step 5로 진행하지 않는다.**

- [ ] **Step 5: push와 배포 확인**

```bash
git push
gh run watch --exit-status
```

기대: 워크플로 성공.

- [ ] **Step 6: 실제 사이트 확인**

`https://sgom.github.io`를 열어 확인한다.

1. 홈에 글 3편이 보인다.
2. 본문 페이지가 열린다.
3. `/search`에서 검색이 동작한다. **로컬 preview와 달리 실제 배포본에서 인덱스가 올라갔는지가 관건이다.**
4. `https://sgom.github.io/rss.xml`이 열린다.
